**Five things worth knowing before starting:**

- **No retraining needed for steps 1–3.** All 12 checkpoints (A/B/C/D × 3 seeds) already exist,
  are proven reproducible, and are exactly what the OOD suites evaluate — this batch is a
  read-only pass over existing `.pth` files, not new training.
- **The OOD suites are already specified, just not wired up.**
  `configs/evaluation_suites.yaml` has `pose_shift` / `low_friction` / `high_friction` /
  `mass_shift` / `combined_ood` blocks per [§11.3](../force_aware_peg_insertion_project.md#113-evaluation-dataset),
  currently commented out; `evaluate_policy.py` has a `NotImplementedError` marking exactly where
  each suite's randomization needs to be applied. This is implementation against an existing
  design, not new design work.
- **The OOD batch is roughly 24× the nominal batch's episode count** — 500 + 500 + 500 + 500 +
  1,000 = 3,000 episodes/checkpoint × 12 checkpoints = 36,000 new episode-evaluations, against
  the 6,000 the nominal suite took. Measure real wall-clock throughput on the first suite
  (`pose_shift`, smallest scope of the five to debug against) before extrapolating a total budget
  for the rest — don't assume the nominal suite's per-episode cost transfers directly, since batch
  composition (64 envs/batch) may behave differently under wider randomization ranges.
- **Two placeholder numbers get resolved *by* this batch, not before it**: `force_limit_threshold`
  (50 N, untuned since 2026-08-08) and jam detection (no signal at all — §22's Jam Rate has been
  `TBD` since Policy A). Don't tune either speculatively ahead of the OOD data — a real
  force/insertion-progress distribution across nominal *and* OOD episodes is the input a real jam
  heuristic needs (§18: "high sustained force, negligible insertion progress, continued contact").
- **`evaluate_policy.py` must be run from the repo root**, not from inside `force_peg_rl/` —
  carried over from the 2026-08-12 doc's own gotcha, still applies to every new suite run.
