**Five things worth knowing before starting:**

- **Run order is B → C → D**, per the prior doc's queue decision — B and C are the
  freshly-verified ablation arms; D is the already-proven-bit-identical baseline
  config and carries no implementation risk, so it goes last.
- **Reuse Policy A's tuned settings exactly**: `--num_envs=512`,
  `agent.params.config.minibatch_size=2048`, `--max_iterations=500`/seed. The naive
  `--num_envs=1024` default with the yaml's `num_actors: 128` mismatched
  `minibatch_size` 8× too many gradient steps/epoch and projected a ~50-hour run —
  don't rediscover that. Even tuned, Policy A's 3 seeds took ~30.5h wall-clock
  because of GPU contention from other processes sharing this box (`bas-zeus`, DGX
  Spark `GB10`) — budget similarly for 9 runs (~90h+) unless contention has cleared,
  and don't kill runs over it without checking first, per the venue decision.
- **This shell runs directly on the training box** — Isaac Lab is installed locally
  at `~/isaac/IsaacLab`, not just reachable via `brev shell isaac-sim`. Any
  `isaaclab.sh -p ...` invocation needs `env -u VIRTUAL_ENV -u CONDA_PREFIX` (an
  unrelated project `.venv` shadows `isaaclab.sh`'s own env-selection logic) and
  `LD_PRELOAD=/lib/aarch64-linux-gnu/libgomp.so.1` (the app's own documented
  shared-library requirement) — found the hard way registering Policy B/C.
- **`evaluate_policy.py` must be run from the repo root**, not from inside
  `force_peg_rl/` — Policy A's CSVs landed in the wrong place
  (`force_peg_rl/results/raw/` instead of `results/raw/`) exactly this way and had
  to be `git mv`'d after the fact. Don't repeat it for B/C/D.
- **Two caveats carry over unchanged from Policy A's results**, worth restating in
  every new results-table entry rather than assuming the reader remembers: (1)
  `termination_reason` is real per-step logging but not real early termination —
  episodes still run to the shared timeout, so force-limit/success rates describe
  *whether the condition was ever true*, not *whether it ended the episode*: and
  `force_limit_threshold = 50.0` is still an untuned placeholder; (2) jam rate is
  not instrumented at all — leave it `TBD` in the results table, don't backfill 0%.

1. **Train Policy B, 3 seeds** (`Shaurya-ForcePegInsert-PolicyB-Direct-v0`,
   `--headless`, tuned settings above, seeds 42/43/44 to match Policy A). Force
   observations in, no contact penalty — tests whether force *information alone*
   (without being penalized for it) changes behavior versus Policy A.

2. **Evaluate Policy B against `nominal`** (`evaluate_policy.py`, 500 deterministic

   trusting the aggregate, same as Policy A's step 4.

3. **Train Policy C, 3 seeds** (`Shaurya-ForcePegInsert-PolicyC-Direct-v0`, same
   settings/seeds). No force observations, but the contact penalty is active — the
   mirror-image ablation: does penalizing force the policy can't directly perceive
   still shape safer behavior, or does it just fight blind?

4. **Evaluate Policy C against `nominal`** — same protocol as step 2.

5. **Train Policy D, 3 seeds** (`Shaurya-ForcePegInsert-Direct-v0`, same
   settings/seeds). Force-aware baseline — both observations and penalty active,
   matching upstream FORGE's default design.

6. **Evaluate Policy D against `nominal`** — same protocol as step 2.
