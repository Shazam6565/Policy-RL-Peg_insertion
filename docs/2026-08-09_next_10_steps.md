**Four things worth knowing before continuing:**

- `termination_reason` is real per-step *logging*, not real early termination —
  episodes still always run to the shared timeout (resets stay synchronized; a
  genuine per-env reset crashed and was correctly deferred, not proven impossible —
  see the 2026-08-08 log's correction). That means §13's "hard-force-limit
  termination rate" and similar metrics, when computed from this run's data, describe
  *whether the condition was ever true during the episode*, not *whether it ended the
  episode* — worth stating explicitly in any results write-up, not discovering at
  report time. `force_limit_threshold = 50.0` is also an untuned placeholder (5× the
  existing soft threshold's upper bound, no real number derived anywhere) — flag it
  as such wherever force-limit rate is cited.
- **Update (2026-08-12):** an actual opt-in early-termination mechanism now exists —
  a `use_early_termination` flag plus a new diagnostic task,
  `Shaurya-ForcePegInsert-EarlyTerm-Direct-v0`, with per-step `debug/n_*` reset
  counters. It defaults to `False` on the shared `ForgeTask`/`ForgeEnvCfg` base, so it
  changed nothing about how Policy A actually trained/evaluated below — but the prior
  bullet's "not implemented" framing is now "implemented, opt-in, unused by default."
  Worth a real decision (not yet made) on whether Policy B/C/D adopt it or stay on the
  same synchronized-timeout approach Policy A used, for apples-to-apples comparability.
- The toggle mechanism built for Policy A generalizes to B and C with **zero new
  code** — per [§12](../force_aware_peg_insertion_project.md#12-experimental-design):
  Policy B = `use_force_obs=True, use_force_penalty=False`, Policy C =
  `use_force_obs=False, use_force_penalty=True`. Just new cfg values + a task
  registration each, same pattern already proven for Policy A.
- Policy D needs **no new registration at all** — the existing
  `Shaurya-ForcePegInsert-Direct-v0` task (both flags default `True`) already *is*
  Policy D, per the very first observation in `next_10_steps.md`. It just needs to go
  through the same real-training → evaluation pipeline as everything else; there's no
  "implement Policy D" step.
